## 1. Spring Boot 3.2.4 + Java 17 

是什么：

- Spring Boot 是 Spring 生态的快速应用脚手架，自动装配、内嵌容器、约定优于配置。
- 项目使用 Java 17，因此代码中大量使用 record、switch 表达式、文本块等特性。

项目实现：

- 启动类入口：`src/main/java/com/hmdp/HmDianPingApplication.java`
- 两个 MapperScan：
  - 扫**主业务**的 Mapper：`com.hmdp.mapper`
  - 扫**AI 模块**的 Mapper：`com.hmdp.ai.mapper`
- 异步能力：`AiAsyncConfiguration` 中定义 `aiAgentTaskExecutor` 线程池。
- 配置绑定：`AiAgentProperties` 绑定 `ai.agent.*`。
- 全局异常：`WebExceptionAdvice`。
- AOP：`SlidingWindowLimitAspect`。

### 1.1 @mapperScan（启动类的技术）：

```java
// HmDianPingApplication.java
@MapperScan("com.hmdp.mapper")
@SpringBootApplication
public class HmDianPingApplication {
    public static void main(String[] args) {
        SpringApplication.run(HmDianPingApplication.class, args);
    }
}
```

AI Mapper 单独扫描：

```java
// AiMapperConfiguration.java
@Configuration
@MapperScan("com.hmdp.ai.mapper")
public class AiMapperConfiguration {
}
```
> **@MapperScan是什么?** <br>MyBatis 整合 Spring Boot 时提供的注解,告诉 Spring Boot 去哪个包路径下扫描 Mapper 接口.<br>简单来说：批量注册 Mapper，省去你挨个给 Mapper 加 `@Mapper` 注解的麻烦。

Q：`@MapperScan` 扫的是接口还是实现类？</br>
A：**扫的是接口**。MyBatis 的 Mapper 都是接口，没有实现类；真正的实现类是 MyBatis 在运行时动态生成的代理对象，`@MapperScan` 只是触发这个生成和注册的过程。


### 1.2异步线程池：
在 `AiAsyncConfiguration` 中定义了 AI 任务专用线程池 `aiAgentTaskExecutor`，并通过 `@EnableAsync` 开启 Spring 异步能力：
```java
// AiAsyncConfiguration.java
@Configuration
@EnableAsync
public class AiAsyncConfiguration {
    @Bean("aiAgentTaskExecutor")
    public Executor aiAgentTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4); //核心线程数4
        executor.setMaxPoolSize(8); //最大线程数8
        executor.setQueueCapacity(200); //队列容量200
        executor.setThreadNamePrefix("ai-agent-");
        executor.initialize();
        return executor;
    }
}
```
- 核心线程数 4、最大线程数 8、队列容量 200，专门承载 AI 异步任务，与主业务线程池隔离；
- 使用时在方法上标注 `@Async("aiAgentTaskExecutor")` 即可将方法提交至该线程池异步执行。

### 1.3配置属性绑定：
通过 `AiAgentProperties` 将配置文件中 `ai.agent` 前缀的配置自动绑定为 Java 对象：
```java
// AiAgentProperties.java
@Data
@ConfigurationProperties(prefix = "ai.agent")
public class AiAgentProperties {
    private Memory memory = new Memory();
    private Rag rag = new Rag();
    private Model model = new Model();
    private Streaming streaming = new Streaming();
    private Mcp mcp = new Mcp();
    //...
}
```
>**@ConfigurationProperties SpringBoot配置绑定注解**
> </br>把配置文件（application.yml/application.properties）中，所有以 `ai.agent` 开头的配置项，自动映射到这个 Java 类的对应字段上。</br>
> 类中的嵌套字段`Memory`、`Rag`、`Model`对应配置文件里的**二级配置项**

>spring流程：
>1. **启动扫描**：Spring Boot 启动时，识别到 `@ConfigurationProperties` 注解的类；
>2. **读取配置**：加载 `application.yml` 里的所有配置；
>3. **前缀匹配**：筛选出所有以 `ai.agent` 开头的配置项；
>4. **反射赋值**：通过反射，把配置值逐个设置到 `AiAgentProperties` 对象的对应字段里；
>5. **注册 Bean**：把填充好的 `AiAgentProperties` 对象注册成 Spring 容器里的 Bean。<br>使用举例`@Autowired
    private AiAgentProperties aiAgentProperties;`

> **好处**：替代 `@Value` 逐个注入，更结构化。</br>`@Value("${ai.agent.rag.top-k}")
private Integer topK;`



### 1.4全局异常处理：
通过 `WebExceptionAdvice` + `@RestControllerAdvice` 实现全局统一异常捕获：避免在每个 Controller 中重复编写 try-catch，统一异常返回格式与日志记录。
```java
// WebExceptionAdvice.java
@RestControllerAdvice
public class WebExceptionAdvice {
    @ExceptionHandler(RateLimitExceededException.class)
    public Result handleRateLimitExceededException(RateLimitExceededException e) {
        return Result.fail("AI 请求过于频繁，请稍后再试");
    }

    @ExceptionHandler(RuntimeException.class)
    public Result handleRuntimeException(RuntimeException e) {
        log.error(e.toString(), e);
        return Result.fail("服务器异常");
    }
}
```
>**类级别@RestControllerAdvice**: </br>
> 标记这个类是全局 REST 异常处理器，Spring 启动时会自动识别并注册。
>它会拦截项目中所有 Controller 抛出的异常。**把所有异常处理抽到一个统一的地方，不侵入业务代码，全局统一拦截、统一处理、统一返回**。

>**方法级别：@ExceptionHandler**:**异常匹配注解**，括号里写「要捕获的异常类型」
> 1. @ExceptionHandler(RateLimitExceededException.class)专门捕获「限流异常」。</br>只要 Controller 或 Service 里抛出这个异常，就会进到这个方法。返回明确的业务提示：`AI 请求过于频繁，请稍后再试`，前端可以直接展示给用户.
> 2. @ExceptionHandler(RuntimeException.class)这是**兜底异常处理**。</br>所有没有被更精准的异常处理器捕获的运行时异常，都会走到这里。
后端记录完整错误日志（`log.error`），方便排查问题,只返回通用的「服务器异常」给前端，**不暴露内部错误细节**，兼顾安全和用户体验。

>返回值 `Result`:这是项目统一的响应结果封装，所有接口（正常响应、异常响应）都返回同一结构

### 1.5 AOP切面
项目通过 `SlidingWindowLimitAspect` 基于 AOP 实现滑动窗口限流，对标注了限流注解的接口自动执行限流逻辑，无需侵入业务代码。
面试追问：

Q：Spring Boot 自动装配是什么？

参考回答：启动类上的 `@SpringBootApplication` 包含 `@EnableAutoConfiguration`，Spring Boot 根据 classpath 中的依赖和配置条件注册 Bean，例如 Redis、Web MVC、RocketMQ Starter 等，开发者不用手写大量 XML。

Q：项目中为什么用 `@TransactionalEventListener`？

参考回答：AI 消息写入数据库后，希望事务提交成功再触发 Agent，避免事务还没提交就开始异步处理，也避免事务回滚后异步任务已经执行。

## 2. MyBatis-Plus 3.5.5

是什么：

MyBatis-Plus 是 MyBatis 增强工具，提供通用 CRUD、Lambda 查询、分页插件和 ActiveRecord 式能力。

项目实现：

- Mapper 继承 `BaseMapper<T>`。
- Service 继承 `IService<T>`，实现类继承 `ServiceImpl<M, T>`。
- 分页插件：`MybatisConfig` 注册 `PaginationInnerInterceptor`。
- 实体注解：`@TableName`、`@TableId`、`@TableField(exist = false)`。

项目真实例子：

- `VoucherOrderServiceImpl.createVoucherOrder` 使用 `seckillVoucherService.update().setSql("stock = stock - 1").eq(...).gt(...).update()`。
- `BlogServiceImpl.queryBlogOfFollow` 使用 `.in("id", ids).last("ORDER BY FIELD(...)")`。

## 3. MySQL

项目核心表：

- `tb_shop`：店铺。
- `tb_voucher` / `tb_seckill_voucher`：优惠券主表与秒杀扩展表。
- `tb_voucher_order`：订单。
- `tb_blog` / `tb_blog_comments` / `tb_follow`：笔记、评论、关注。
- `tb_user` / `tb_user_info`：用户。
- `tb_ai_conversation` / `tb_ai_message`：AI 会话与消息。

AI 表索引：

- `tb_ai_conversation(user_id, status, updated_time)`
- `tb_ai_message(conversation_id, created_time)`

关键关系：

```text
tb_shop 1 ─── N tb_voucher
tb_voucher 1 ─── 0..1 tb_seckill_voucher
tb_voucher_order 1 ─── 1 tb_voucher
tb_blog N ─── 1 tb_shop
tb_follow(user_id, follow_user_id) 表示用户关注关系
tb_ai_conversation 1 ─── N tb_ai_message
```

项目中的 SQL 与事务：

```java
// ShopServiceImpl.update：先更新数据库，再删缓存
@Transactional
public Result update(Shop shop) {
    updateById(shop);
    stringRedisTemplate.delete(CACHE_SHOP_KEY + id);
    return Result.ok();
}
```

```java
// VoucherOrderServiceImpl.createVoucherOrder：订单与库存同一事务
@Transactional(rollbackFor = Exception.class)
public void createVoucherOrder(VoucherOrder voucherOrder) {
    save(voucherOrder);
    boolean stockUpdated = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherOrder.getVoucherId())
            .gt("stock", 0)
            .update();
    if (!stockUpdated) {
        throw new IllegalStateException("扣减秒杀库存失败");
    }
}
```

为什么订单和库存要在同一个事务里：

- 如果订单保存成功但库存扣减失败，会产生“有订单、没扣库存”的不一致。
- 放在同一事务中，库存扣减失败会回滚已保存的订单。

为什么 `tb_seckill_voucher` 要和 `tb_voucher` 拆开：

- `tb_voucher` 是优惠券主表，普通券和秒杀券共用标题、规则、金额等字段。
- `tb_seckill_voucher` 只有秒杀券需要的库存、起止时间等字段。
- 拆表后普通券不需要承载秒杀字段，避免大量空列；同时秒杀库存更新不会影响普通券主表。

面试追问：

Q：为什么秒杀订单主键不用数据库自增？

参考回答：秒杀场景需要提前生成全局唯一订单 ID，避免数据库自增成为热点；项目用 `RedisIdWorker` 基于 Redis `INCR` 生成。同时订单 ID 不暴露自增规律，也更适合后续分库分表。

## 4. Redis（面试级）

### 4.1 Redis 在项目中的角色

是什么：

Redis 是内存数据结构服务器，支持 String、Hash、List、Set、ZSet、Bitmap、GEO、HyperLogLog、Stream 等。

项目实现：

项目同时使用两个客户端：

- `StringRedisTemplate`：大多数缓存、锁、脚本、GEO、ZSet 操作。
- `RedissonClient`：布隆过滤器、`RScript` 执行限流 Lua。

配置位置：

- `RedisConfig`
- `RedissonConfig`

面试追问：

Q：为什么同时用 `StringRedisTemplate` 和 `RedissonClient`？

参考回答：`StringRedisTemplate` 适合基础命令和脚本，代码直观；`RedissonClient` 提供高级对象，例如 `RBloomFilter`、`RScoredSortedSet`、`RScript`，适合布隆过滤器和复杂限流。项目按能力选型，而不是统一替换。

### 4.2.1 String：店铺缓存和空值缓存

`CacheClient.queryWithPassThrough` 的完整决策：

```java
public <R, ID> R queryWithPassThrough(
        String keyPrefix, ID id, Class<R> type,
        Function<ID, R> dbFallback, Long time, TimeUnit unit) {
    String key = keyPrefix + id;

    // 1. 查 Redis
    String json = stringRedisTemplate.opsForValue().get(key);

    // 2. 有真实值
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, type);
    }

    // 3. 命中空字符串
    if (json != null) {
        return null;
    }

    // 4. 回源 MySQL
    R r = dbFallback.apply(id);

    // 5. 数据库也没有：写空值
    if (r == null) {
        stringRedisTemplate.opsForValue()
                .set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
        return null;
    }

    // 6. 数据库有：写真实缓存
    this.set(key, r, time, unit);
    return r;
}
```

### 4.2.3 String：Redis 全局 ID

`RedisIdWorker`：

```java
public long nextId(String keyPrefix) {
    LocalDateTime now = LocalDateTime.now();
    long timestamp = now.toEpochSecond(ZoneOffset.UTC) - BEGIN_TIMESTAMP;
    String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
    long count = stringRedisTemplate.opsForValue()
            .increment("icr:" + keyPrefix + ":" + date);
    return timestamp << COUNT_BITS | count;
}
```

ID 结构：

```text
高 31 位：相对时间戳（秒）
低 32 位：当天 Redis 自增序列
```

好处：

- 不依赖 MySQL 自增，可分布式生成。
- 按天重置序列，避免单个 key 无限增长。
- 生成速度高于数据库自增。

### 4.2.7 Bitmap：签到


签到本质：

- 一个月的第 N 天对应 bitmap 的第 N-1 位。
- `SETBIT` 设置某天是否签到。
- `BITFIELD` 读回一个整数，再从低位统计连续 `1`。

### 4.2.8 Redis 是缓存还是存储

项目中 Redis 承担两种角色：

1. 缓存：店铺详情、验证码、token，可以丢失后回源重建。
2. 业务状态：库存、一人一单、点赞、关注、GEO、签到，丢失会影响业务正确性。

这是面试中很重要的区分。

面试追问：

Q：为什么很多 Key 没有设置 TTL？

参考回答：不同数据生命周期不同。库存、点赞、关注、GEO 这类数据不是普通“缓存”，删除会破坏业务状态，因此由业务逻辑维护。严格说它们更像是 Redis 作为存储或实时状态，而不是单纯缓存。生产上仍需要评估内存增长和数据恢复方案。

Q：`seckill:stock` 没有 TTL 会有什么问题？

参考回答：好处是秒杀期间库存不能过期；风险是如果某个秒杀活动结束后没有清理，会一直占用内存。当前项目靠启动预热、失败回滚和人工重建维护，但没有统一的“活动结束清理任务”。

### 4.3 Cache Aside 模式

是什么：

读缓存时先查缓存，未命中再查数据库并回写；更新时先更新数据库，再删除缓存，让下次读请求回源重建。

项目实现：

- 读：`ShopServiceImpl.queryById` 调用 `CacheClient.queryWithPassThrough`。
- 更新：`ShopServiceImpl.update` 先 `updateById`，再删除 `cache:shop:{id}`。

真实代码：

```java
// ShopServiceImpl.update
updateById(shop);
stringRedisTemplate.delete(CACHE_SHOP_KEY + id);
```

面试追问：

Q：为什么不直接更新缓存，而是删除缓存？

参考回答：直接更新缓存存在并发覆盖风险，例如两个写请求顺序不同，可能把旧值写回。删除缓存让下一次读回源，更简单。缺点是删除后第一次读会打库。

Q：先更新数据库再删缓存，一定一致吗？

参考回答：不是绝对一致。若读请求在“数据库已更新、缓存未删除”之间读到旧缓存，会出现短暂不一致。生产可用延迟双删、binlog 订阅、版本号等方式进一步处理。

### 4.4 缓存穿透

是什么：

查询一个数据库中根本不存在的数据，导致每次请求都绕过缓存打到数据库。

项目实现：

两层防护：

1. 布隆过滤器：

```java
if (!shopBloomFilter.contains(id)) {
    return Result.fail("店铺不存在");
}
```

2. 空对象缓存：

`CacheClient.queryWithPassThrough` 在 DB 返回 null 时写空字符串，TTL 2 分钟。

初始化：

`BloomFilterInitializer` 启动时删除旧 key、`tryInit`、分页加载店铺和优惠券 ID。

面试追问：

Q：布隆过滤器有误判，为什么还要空对象缓存？

参考回答：布隆过滤器说“存在”时可能误判，漏过去的请求仍会打库；空对象缓存把第一次打库后的结果也缓存住，避免后续重复打库。

Q：布隆过滤器能否删除元素？

参考回答：标准 Bloom Filter 不支持精确删除。新增店铺时项目会 `add(id)`，但删除店铺不会移除 bit，可能长期保留。可通过定期重建或 Cuckoo Filter 等方案缓解。

### 4.5 缓存击穿

是什么：

一个热点 key 过期瞬间，大量请求同时回源数据库，导致数据库压力骤增。

项目实现：

`CacheClient` 同时实现了两种方案：

- `queryWithMutex`：抢锁成功才重建，抢锁失败 sleep 后重试。
- `queryWithLogicalExpire`：逻辑过期后当前请求返回旧数据，后台线程重建。

当前 `ShopServiceImpl` 实际使用 `queryWithPassThrough`，但两个击穿方法已实现并保留注释。

面试追问：

Q：互斥锁和逻辑过期怎么选？

参考回答：互斥锁一致性好，但抢不到锁的请求可能等待；逻辑过期可用性高，但短时间返回旧数据。店铺详情可容忍短暂旧数据，所以适合逻辑过期；资金、库存等强一致场景更偏向互斥锁。

Q：项目为什么当前没有切换逻辑过期？

参考回答：这是项目可继续完善的点。切换需要预热时使用 `setWithLogicalExpire`，读取时调用 `queryWithLogicalExpire`。代码能力已经具备，当前默认配置仍以穿透 + 布隆过滤器为主。

### 4.6 缓存雪崩

是什么：

大量 key 在同一时间过期，或 Redis 整体故障，导致数据库瞬间承受巨大压力。

项目实现：

- 不同类型数据 TTL 不同：登录验证码 2 分钟、店铺缓存 30 分钟、空值 2 分钟。
- `CacheClient` 已实现逻辑过期方案。
- 入口有 `SlidingWindowLimitAspect` 限流。
- 秒杀库存、关注、点赞、GEO 等不设置 TTL，避免业务状态同时过期。

需要诚实说明：

项目没有显式做“TTL 随机偏移”，因此雪崩防护更多是分层和限流，而不是完整落地随机过期。

面试追问：

Q：如果让你继续完善，你会怎么做？

参考回答：对缓存 TTL 增加随机偏移；核心热点数据使用逻辑过期；接入 Redis 集群/哨兵提升可用性；对 DB 连接池和慢查询做保护；关键接口继续限流降级。

### 4.7 Lua

是什么：

Lua 脚本可以一次性提交给 Redis，脚本执行期间不会被其他客户端命令插入，因此具备原子性。

项目实现：

三处 Lua：

1. `seckill.lua`：秒杀库存预扣和一人一单。
2. `unlock.lua`：分布式锁安全释放。
3. `SlidingWindowLimitAspect`：内联滑动窗口限流脚本。

`seckill.lua` 真实逻辑：

```lua
local stock = tonumber(redis.call('get', stockKey))
if(not stock) then return 3 end
if(stock <= 0) then return 1 end
if(redis.call('sismember', orderKey, userId) == 1) then return 2 end
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
return 0
```

Java 调用：

```java
stringRedisTemplate.execute(
    SECKILL_SCRIPT,
    Collections.emptyList(),
    voucherId.toString(),
    userId.toString()
);
```

面试追问：

Q：Lua 为什么能防止并发问题？

参考回答：Redis 单线程执行命令，Lua 脚本作为整体执行，库存检查和扣减之间不会插入其他客户端命令。

Q：`seckill.lua` 没有使用 KEYS，而是使用 ARGV 构造 key，有什么风险？

参考回答：在单机 Redis 下没问题；但在 Redis Cluster 中，`seckill:stock:{id}` 和 `seckill:order:{id}` 可能落在不同 slot，跨 slot Lua 会失败。生产若上集群，需要统一 hash tag，例如 `seckill:{voucherId}:stock` 和 `seckill:{voucherId}:order`。

### 4.8 一人一单

是什么：

限制同一个用户对同一个秒杀券只能成功下单一次。

项目实现：

`seckill.lua` 使用 Set：

- key：`seckill:order:{voucherId}`
- member：`userId`
- 先 `SISMEMBER` 判断，再 `SADD`。

失败补偿：

`rollbackSeckillReservation` 会执行：

```java
stringRedisTemplate.opsForSet().remove(
    SECKILL_ORDER_KEY_PREFIX + voucherId,
    String.valueOf(userId)
);
```

面试追问：

Q：为什么用 Redis Set，而不是 MySQL 唯一索引？

参考回答：秒杀入口要先在 Redis 快速判断，MySQL 是异步落库，不能作为第一道防线。理想情况下 MySQL 也应加 `(voucher_id, user_id)` 唯一索引作为最终兜底，但当前代码主要依赖 Redis Set。

Q：如果 Redis 重启，`seckill:order:{voucherId}` 丢了怎么办？

参考回答：会出现同一用户重复下单风险。生产需要 Redis 持久化/集群，或数据库唯一索引兜底。

### 4.9 超卖

是什么：

卖出的数量超过实际库存。

项目实现：

双重保护：

1. Redis 预扣：

```lua
if(stock <= 0) then return 1 end
redis.call('incrby', stockKey, -1)
```

2. MySQL 最终扣减：

```java
seckillVoucherService.update()
    .setSql("stock = stock - 1")
    .eq("voucher_id", voucherOrder.getVoucherId())
    .gt("stock", 0)
    .update();
```

如果 MySQL 扣减失败：

- 回滚 Redis 库存和一人一单 Set。
- 抛异常触发 MQ 重试。

面试追问：

Q：Redis 已经扣了，为什么 MySQL 还要再扣一次？

参考回答：Redis 是快速预扣，MySQL 是最终持久化库存。二者形成“预扣 + 确认”结构，防止最终数据不一致。

Q：`stock = stock - 1 where stock > 0` 为什么能防超卖？

参考回答：数据库更新条件带 `stock > 0`，当库存为 0 时影响行数为 0，更新失败，事务回滚，不会继续扣成负数。

### 4.10 分布式锁

是什么：

在多个 JVM/实例之间保证同一时刻只有一个线程能执行临界区。

项目实现：

`SimpleRedisLock`：

加锁：

```java
setIfAbsent(KEY_PREFIX + name, threadId, leaseTime, TimeUnit.SECONDS);
```

锁值：

```text
UUID-ThreadId
```

解锁：

执行 `unlock.lua`，先比较 value，一致才删除。

使用位置：

- 支付回调：`lock:order:payment:{orderId}`
- 超时关单：`lock:order:timeout:{orderId}`

另外，`CacheClient` 内部还有一套简单的缓存重建锁：

```java
setIfAbsent(key, "1", 10, TimeUnit.SECONDS)
```

注意：

`CacheClient` 这套锁的 value 固定为 `"1"`，`unlock` 直接 delete，没有做“持有者判断”。它只用于缓存重建，风险相对低；而 `SimpleRedisLock` 才是带 UUID 和 Lua 解锁的正式锁。

面试追问：

Q：手写 Redis 锁有什么问题？

参考回答：锁续期、可重入、红锁、主从切换等复杂场景没有处理。项目业务锁时间短，简单实现够用；生产上可以换 Redisson `RLock`，它提供看门狗续期和可重入能力。

Q：锁过期了怎么办？

参考回答：如果业务执行超过 leaseTime，锁可能被误释放。简单实现无法续期；Redisson 看门狗可以在业务未完成时自动续期。

`RocketMQConstants`

### 5.2 Topic 与 Consumer Group

是什么：

- Topic：消息主题，生产者发送和消费者订阅的逻辑分类。
- Tag：Topic 下的二级过滤。
- Consumer Group：一组消费者，集群模式下同一消息只被组内一个消费者消费。

项目真实定义：

```text
SECKILL_ORDER_TOPIC     = seckill-order-topic
SECKILL_ORDER_TAG       = create
SECKILL_ORDER_DESTINATION = seckill-order-topic:create
SECKILL_ORDER_CONSUMER_GROUP = hmdp-seckill-order-consumer

ORDER_TIMEOUT_TOPIC     = order-timeout-topic
ORDER_TIMEOUT_TAG       = close

ORDER_TIMEOUT_CONSUMER_GROUP = hmdp-order-timeout-consumer
```

面试追问：

Q：为什么拆两个 Topic？

参考回答：业务语义不同。一个是“创建秒杀订单”，另一个是“15 分钟后关单”。拆开后消费者可独立扩容、独立重试、独立监控。

### 5.3 Producer

项目实现：

`VoucherOrderServiceImpl.seckillVoucher`：

```java
// 1. Redis Lua 预扣成功后，构造 VoucherOrder
VoucherOrder order = new VoucherOrder();
order.setId(orderId);
order.setUserId(userId);
order.setVoucherId(voucherId);
order.setStatus(VoucherOrder.STATUS_UNPAID);

// 2. 标记订单 pending，供前端状态查询和失败补偿使用
markOrderPending(orderId, userId);

try {
    // 3. 同步发送创建订单消息
    rocketMQTemplate.syncSend(
        RocketMQConstants.SECKILL_ORDER_DESTINATION,
        objectMapper.writeValueAsString(order)
    );
} catch (Exception e) {
    // 发送失败：清理 pending，并回滚 Redis 预扣
    clearOrderPending(orderId);
    rollbackSeckillReservation(voucherId, userId);
    return Result.fail("订单创建失败，请稍后重试");
}

try {
    // 4. 发送 15 分钟延迟关单消息
    rocketMQTemplate.syncSendDelayTimeMills(
        RocketMQConstants.ORDER_TIMEOUT_DESTINATION,
        String.valueOf(orderId),
        RocketMQConstants.ORDER_PAYMENT_TIMEOUT_MILLIS
    );
} catch (Exception e) {
    log.error("订单超时延迟消息发送失败，订单ID: {}", orderId, e);
}

return Result.ok(orderId);
```

消息体：

- 下单消息：JSON 化的 `VoucherOrder`。
- 延迟消息：只发送 `orderId` 字符串。

这段代码体现的工程细节：

- 下单消息发送失败会回滚 Redis，避免“Redis 已扣但消息没发出”。
- 延迟消息失败只记录日志，因为下单主流程不应因关单失败而阻塞；但这也留下了补偿风险。

面试追问：

Q：同步发送和异步发送有什么区别？

参考回答：同步发送等待 Broker 确认，可靠性相对更高，但阻塞当前线程；异步发送不阻塞但需要回调。秒杀下单链路需要确定消息是否成功，以便失败时回滚 Redis，所以这里用同步发送。

### 5.4 Consumer

项目实现：

`SeckillVoucherListener`：

```java

    topic = RocketMQConstants.SECKILL_ORDER_TOPIC,

    consumeMode = ConsumeMode.CONCURRENTLY,

```

收到消息后反序列化并调用：


面试追问：

Q：`CLUSTERING` 和 `BROADCASTING` 有什么区别？

参考回答：`CLUSTERING` 下同一 Consumer Group 的多个实例负载均衡消费，适合订单处理；`BROADCASTING` 下每个实例都会收到全部消息，适合缓存刷新、广播通知。

### 5.5 异步化

是什么：

把耗时或非核心操作从主请求中剥离，通过消息队列异步处理。

项目实现：

秒杀主链路只做：

1. Redis Lua 预扣。
2. 发送创建订单消息。
3. 发送延迟关单消息。
4. 立即返回订单 ID。

MySQL 落库由 `SeckillVoucherListener` 异步完成。

面试追问：

Q：异步化带来什么代价？

参考回答：系统从强一致变成最终一致，用户可能短时间查到 pending 状态；需要幂等、补偿、状态查询来兜底。

### 5.6 延迟消息

是什么：

消息发送后不立即投递给消费者，而是延迟指定时间后再投递。

项目实现：

下单成功发送一条 15 分钟延迟消息：

```java
ORDER_PAYMENT_TIMEOUT_MILLIS = TimeUnit.MINUTES.toMillis(15)
```

消费者收到后关闭未支付订单并回滚库存。

面试追问：

Q：如果延迟消息发送失败会怎样？

参考回答：当前代码只记录日志，不中断下单主流程。这意味着订单可能永远不自动关闭，库存也不会自动回滚。生产上需要定时扫描超时未支付订单作为补偿。

### 5.7 消费失败与重试

项目实现：

消费者捕获异常后抛 `IllegalStateException`，交给 RocketMQ 重试。

Q：重试会导致什么问题？

### 5.8 幂等

项目实现：

创建订单时先查是否已存在：

```java

    clearOrderPending(voucherOrder.getId());

}
```

关单时检查订单状态：

```java

    return;
}
```

面试追问：

Q：除了业务判重，还有什么幂等方案？

参考回答：数据库唯一索引、Redis SETNX、消息 ID 去重表、状态机约束。项目用的是“业务 ID + 状态判断”。

### 5.9 消息丢失与重复消费

项目已做的：

- 秒杀下单消息发送失败：清理 pending，回滚 Redis 库存和一人一单 Set。
- 消费失败：抛异常重试。
- 消费重复：订单 ID 幂等。

项目仍存在的风险：

- Redis Lua 预扣成功后，进程崩溃在“发送 MQ 之前”，会留下 Redis 预扣但没有消息，缺少事务消息/本地消息表补偿。
- 延迟关单消息发送失败只打日志，缺少补偿扫描。
- Broker 刷盘、主从同步等可靠性依赖 RocketMQ 部署配置，项目代码未覆盖。

面试追问：

Q：如何进一步解决“Redis 预扣成功但消息没发出”？

参考回答：引入本地消息表或事务消息：先写一条待发送记录，再发 MQ，发送成功后更新状态；定时任务扫描未发送记录进行补偿。RocketMQ 本身支持事务消息，也可以使用。

## 6. RAG（面试级）

### 6.1 什么是 RAG

RAG（Retrieval-Augmented Generation）是“检索增强生成”：

1. 先把知识库文档切块并向量化，写入向量数据库。
2. 用户提问时，把问题向量化。
3. 在向量库中检索最相关的 Top-K 文档。
4. 把检索结果作为上下文交给 LLM。
5. LLM 基于真实资料生成答案。

### 6.2 项目真实 RAG 全链路

#### 索引写入链路

```text
应用启动
  │
  ▼
KnowledgeBaseInitializer
  → AiVectorIndexService.ensureInitialized()
       ├─ 知识库为空 → rebuildKnowledge()
       ├─ 店铺画像为空 → rebuildAllShopProfiles()
       └─ 评论为空 → rebuildAllBlogReviews()
  │
  ▼
AiVectorIndexServiceImpl
  ├─ 知识库：
  │     classpath:knowledge/*.txt
  │     → TextReader 读取
  │     → TokenTextSplitter 切块
  │     → Document 增加 docType=knowledge 等 metadata
  │     → knowledgeVectorStore.add(documents)
  │
  ├─ 店铺画像：
```

### 6.3 为什么需要 Embedding

是什么：

Embedding 把文本映射成高维向量，让语义相近的文本在向量空间中距离更近。

项目实现：

配置使用阿里 DashScope 兼容接口：

```yaml
spring.ai.openai.embedding.options.model: text-embedding-v4
spring.ai.vectorstore.milvus.embedding-dimension: 1024
```

Spring AI 的 `EmbeddingModel` 负责把 query 和文档转成向量，`MilvusVectorStore` 内部调用它。

面试追问：

Q：为什么不能只用 MySQL LIKE 做检索？

参考回答：LIKE 只能做关键词字面匹配，无法理解“火锅”和“涮羊肉”“烤肉”等语义相近的词。Embedding 能把语义相近的文本映射到相近向量，解决语义检索问题。

### 6.4 为什么使用 Milvus

是什么：

Milvus 是面向向量的分布式数据库，专为大规模向量存储和相似度检索设计。

项目实现：

- 三个 collection：
  - `knowledge_vector`
  - `shop_profile_vector`
  - `blog_review_vector`
- `CommonConfiguration` 创建 `MilvusServiceClient` 和三个 `VectorStore` Bean。
- 检查 collection 维度，维度不匹配时按 `initialize-schema` 配置处理。

面试追问：

Q：MySQL 或 Redis 也能存向量，为什么用 Milvus？

参考回答：MySQL 没有高效的向量近似检索能力；Redis 可以做简单向量检索，但大规模、多集合、metadata 过滤、索引管理和扩展性不如专门向量数据库。Milvus 支持 HNSW/IVF 等索引、标量过滤、批量写入和水平扩展。

### 6.5 Vector Search 怎么工作

是什么：

把 query 向量和库中每个文档向量计算相似度，返回最接近的 K 个结果。

项目实现：

Java 层没有直接写“计算余弦相似度”的循环，而是调用 Spring AI 抽象：

```java
VectorStore.similaritySearch(SearchRequest)
```

内部：

1. `EmbeddingModel` 把 query 转为向量。
2. Milvus 使用自身索引做相似度检索。
3. 返回带 score 的 `Document`。

项目里 `VectorDistanceUtils` 也提供了欧氏距离和余弦相似度工具方法，但 main 业务链路没有直接调用。

面试追问：

Q：向量检索为什么比全量扫描快？

参考回答：Milvus 用 ANN 索引，例如 HNSW、IVF，先用索引快速定位候选集合，再精确计算少量候选，避免和全部向量比较。

Q：项目用哪种距离度量？

参考回答：代码没有显式指定，通常由 Spring AI/Milvus 默认配置决定。面试时可以说明自己知道余弦相似度和欧氏距离，但本项目没有在业务代码中固定距离公式。

### 6.6 Top-K 是什么

是什么：

向量检索返回的候选文档数量，也就是“最相似的 K 条”。

项目实现：

默认值来自：

```yaml
ai.agent.rag.top-k: 5
```

代码：

```java
SearchRequest.builder()
    .query(query)
    .topK(topK)
    .build();
```

不同集合都使用这个配置，但工具调用时可以传入 `topK` 覆盖。

面试追问：

Q：Top-K 太大或太小有什么影响？

参考回答：太小可能漏掉关键信息；太大会引入噪声、增加 token、稀释相关性。项目知识库使用 topK=5，评论/店铺也默认 5，属于相对保守的召回数量。

### 6.7 Chunk 怎么划分

是什么：

把长文档切成适合向量化和检索的小块。

项目实现：

- 知识库：`TokenTextSplitter` 对 `knowledge/*.txt` 切块。
- 店铺画像：一个店铺生成一个 Document，文本由结构化字段拼成。
- 探店评论：一篇 blog 生成一个 Document，文本为“标题 + 店铺名 + 正文”。

代码：

```java
TokenTextSplitter tokenTextSplitter = new TokenTextSplitter();
List<Document> splitDocuments = tokenTextSplitter.apply(reader.get());
```

面试追问：

Q：为什么不把所有文档都按固定字符切？

参考回答：不同类型数据粒度不同。知识库文档长，需要切块保证召回粒度；店铺画像是结构化对象，自然按店铺为单位；评论本身就是一条内容，按篇即可。

### 6.8 为什么会召回错误内容

常见原因：

- Embedding 模型对领域词理解不足。
- query 太短或太模糊。
- chunk 太长，包含多种语义。
- chunk 太短，缺少上下文。
- Top-K 太大，混入低相关文档。
- similarity threshold 设置不合适。
- metadata filter 过宽，没有限定范围。

项目实现中的实际应对：

知识库采用“向量召回 + 关键词 fallback”，解决高确定性规则弱召回的问题。

面试追问：

Q：项目怎么降低知识库弱召回？

参考回答：`AiRagRetriever.searchKnowledge` 先做向量检索，再对 classpath 知识文本做关键词扫描；如果 fallback 有结果，就和相关向量结果合并、去重、排序，最终限制 Top-K。

### 6.9 Metadata Filter 是干什么的

是什么：

Metadata 是文档附带的标量属性，例如 `docType`、`shopId`、`typeId`。Metadata Filter 可以在向量检索前后过滤文档。

项目实现：

删除文档时：

```java
knowledgeVectorStore.delete(
    new FilterExpressionBuilder()
        .eq(AiMetadataConstants.DOC_TYPE, AiMetadataConstants.DOC_TYPE_KNOWLEDGE)
        .build()
);
```

按店铺检索评论时：

```java
Filter.Expression filterExpression =
    new FilterExpressionBuilder()
        .eq(AiMetadataConstants.SHOP_ID, shopId)
        .build();
```

面试追问：

Q：Metadata Filter 和向量检索是什么关系？

参考回答：向量负责语义召回，metadata 负责限定业务范围。例如“只看某店铺的评论”，先按 `shopId` 过滤，再在范围内做向量相似度检索。

### 6.10 RAG 为什么能减少模型幻觉

核心原因：

- 模型生成时不再只依赖参数记忆，而是拿到真实文档作为上下文。
- 检索结果提供可追溯依据。
- 项目提示词明确要求“严禁虚构店铺信息”。

项目实现：

`DianPingAgentTools` 提供 `getShopDetail`、`searchKnowledgeBase`、`vectorSearchShopProfiles` 等工具，模型被要求优先调用工具获取真实数据。

面试追问：

Q：RAG 能完全消除幻觉吗？

参考回答：不能。RAG 只能降低“无依据编造”的概率。如果检索本身召回错误、模型过度发挥、或上下文中信息矛盾，仍可能出错。所以还要做阈值、来源标注、提示词约束和人工评测。

## 7. 其他关键技术

### 7.1 滑动窗口限流

是什么：

把时间窗口细分为连续时间区间，统计真实时间窗口内的请求数。

项目实现：

`SlidingWindowLimitAspect` 使用注解 + AOP + Redis ZSet + Lua。

```text
ZREMRANGEBYSCORE 删除过期元素
ZCOUNT 统计窗口内数量
ZADD 记录当前请求
EXPIRE 设置 key 过期
```

Key：

- 全局：`rate_limit:global:{spelKey}:{value}`
- 用户级：`rate_limit:{userId}:{spelKey}:{value}`

真实 AOP 代码：

```java
// SlidingWindowLimitAspect
@Aspect
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 20)
public class SlidingWindowLimitAspect {
    @Around("@annotation(slidingWindowLimit)")
    public Object around(ProceedingJoinPoint joinPoint,
                         SlidingWindowLimit slidingWindowLimit) throws Throwable {
        ServletRequestAttributes attributes =
                (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
        if (attributes == null) {
            return joinPoint.proceed();
        }

        Object parseSpEL = parseSpEL(joinPoint, signature, slidingWindowLimit.keySpEL());
        String rateLimitKey = buildRateLimitKey(parseSpEL, slidingWindowLimit);

        if (isRateLimited(rateLimitKey, windowSize, timeUnit, maxRequests)) {
            throw new RateLimitExceededException("Rate limit exceeded");
        }

        return joinPoint.proceed();
    }
}
```

Lua 核心：

```lua
ZREMRANGEBYSCORE KEYS[1] -inf windowStartTime
local count = ZCOUNT KEYS[1] windowStartTime currentTime
if maxRequests > 0 and count >= maxRequests then
    return 1
end
ZADD KEYS[1] currentTime requestId
EXPIRE KEYS[1] expireSeconds
return 0
```

### 7.3 登录与 ThreadLocal

项目实现：

- `RefreshTokenInterceptor`：读 token → Redis Hash → `UserHolder` → 续期。
- `LoginInterceptor`：判断 `UserHolder` 是否有用户。
- `afterCompletion`：清理 ThreadLocal。

```java
// RefreshTokenInterceptor
@Override
public boolean preHandle(HttpServletRequest request,
                         HttpServletResponse response,
                         Object handler) {
    String token = request.getHeader("authorization");
    if (StrUtil.isBlank(token)) {
        return true;
    }

    Map<Object, Object> userMap = stringRedisTemplate.opsForHash()
            .entries(LOGIN_USER_KEY + token);
    if (userMap.isEmpty()) {
        return true;
    }

    UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);
    UserHolder.saveUser(userDTO);
    stringRedisTemplate.expire(LOGIN_USER_KEY + token,
            LOGIN_USER_TTL, TimeUnit.MINUTES);
    return true;
}

@Override
public void afterCompletion(...) {
    UserHolder.removeUser();
}
```

```java
// LoginInterceptor
@Override
public boolean preHandle(...) {
    if (UserHolder.getUser() == null) {
        response.setStatus(401);
        return false;
    }
    return true;
}
```

面试追问：

Q：为什么 ThreadLocal 最后要清理？

参考回答：Web 容器线程会复用，不清理可能把上一个请求的用户信息带到下一个请求，导致越权。

### 7.4 事务边界

项目关键事务：

- `createVoucherOrder`：秒杀订单落库。
- `closeTimeoutOrder`：超时关单。

`seckillVoucher` 主链路不做 DB 事务，因为它是 Redis 预扣 + MQ 异步；最终一致性由消费者事务和补偿完成。
