# 四类请求链路详解

本项目至少有四条必须掌握的链路：普通业务、Redis 缓存、秒杀、Agent。

## 1. 普通业务请求链路：GET /shop/{id}

代表场景：用户打开店铺详情。

```text
Client
  │ GET /shop/1 + Authorization
  ▼
DispatcherServlet
  │
  ├─ SlidingWindowLimitAspect（ShopController 类级全局限流）
  ├─ RefreshTokenInterceptor：有 token 则恢复 UserHolder 并续期
  ├─ LoginInterceptor：/shop/** 被排除，无需登录
  ▼
ShopController.queryShopById(id)
  ▼
ShopServiceImpl.queryById(id)
  ├─ shopBloomFilter.contains(id)：不存在直接失败
  ├─ cacheClient.queryWithPassThrough("cache:shop:", id, ...)
  │     ├─ Redis GET cache:shop:1
  │     │     ├─ 有值：JSON 反序列化后返回
  │     │     ├─ 空字符串：命中空缓存，返回 null
  │     │     └─ 无值：调用 this::getById 查 MySQL
  │     └─ DB 为空则写 2 分钟空值；有值则写 30 分钟缓存（正常数据有代码帮你删缓存，TTL 可以大；空缓存没人帮你删，TTL 必须小。）
  └─ 包装成 Result.ok(shop)
```

为什么“普通业务”但包含缓存？

店铺详情是高频读，天然要缓存。这里展示的是最典型的 Controller → Service → Cache/DB 调用链。

另一个普通业务链路：`POST /user/login`。

```text
UserController.login
  → UserServiceImpl.login
     ├─ 校验手机号格式
     ├─ 从 Redis 取验证码并比对
     ├─ 无用户则 createUserWithPhone 落库
     ├─ 生成 token，把 UserDTO 写入 Redis Hash
     └─ 返回 token
```

## 2. Redis 缓存请求链路

### 2.1 缓存穿透链路：店铺不存在 ID

```text
ShopServiceImpl.queryById(999999)
  │
  ├─ 布隆过滤器 miss → Result.fail("店铺不存在")
  │
  └─ 若布隆过滤器误判为可能存在
       CacheClient.queryWithPassThrough
         ├─ Redis GET cache:shop:999999 → null
         ├─ MySQL getById(999999) → null
         └─ Redis SET cache:shop:999999 "" TTL 2min
```

两层防护：

1. 布隆过滤器先拦截绝大多数不存在 ID。
2. 漏网请求查询 MySQL 后写空对象，短 TTL 内不再打库。

### 2.2 缓存击穿链路：热点 key 过期

代码中 `CacheClient` 提供了两种实现：

- 互斥锁：`queryWithMutex`
- 逻辑过期：`queryWithLogicalExpire`

`ShopServiceImpl` 当前启用的注释里保留了这两种方案，默认使用 `queryWithPassThrough`。面试时要把“代码怎么实现”讲清楚。

互斥锁流程：

```text
Redis miss
  → tryLock(lock:shop:{id})
      ├─ 抢到锁：查 MySQL → 写缓存 → 释放锁 → 返回
      └─ 没抢到：sleep(50ms) → 递归重试
```

逻辑过期流程：

```text
Redis GET → RedisData
  ├─ 未过期：返回 data
  └─ 已过期：
       tryLock 成功后提交后台线程重建缓存
       当前请求直接返回旧 data，保证不阻塞
```

### 2.3 附近店铺链路：GET /shop/of/type?x=...&y=...

```text
ShopController.queryShopByType
  → ShopServiceImpl.queryShopByType
     ├─ 无坐标：MySQL 分页
     └─ 有坐标：
          Redis GEOSEARCH shop:geo:{typeId}
             BYLONLAT x y BYRADIUS 5000 WITHDISTANCE
          → 解析 shopId + distance
          → MySQL IN + ORDER BY FIELD(id,...)
          → 回填 distance
```

Redis 在这个项目里承担的职责：

| 数据结构 | 典型 key | 用途 |
| --- | --- | --- |
| String | `cache:shop:{id}` | 对象缓存 |
| String | `seckill:stock:{voucherId}` | 秒杀库存 |
| String | `seckill:order:pending:{orderId}` | 异步下单 pending |
| Hash | `login:token:{token}` | 登录态 |
| ZSet | `blog:liked:{blogId}` | 点赞用户与时间 |
| ZSet | `feed:{userId}` | 粉丝收件箱/关注流 |
| Set | `follows:{userId}` | 关注关系 |
| Set | `seckill:order:{voucherId}` | 一人一单 |
| GEO | `shop:geo:{typeId}` | 附近搜索 |
| Bitmap | `sign:{userId}:yyyyMM` | 每日签到 |
| Bloom | `bloom:shop`、`bloom:voucher` | 防穿透 |

## 3. 秒杀请求链路：POST /voucher-order/seckill/{id}

秒杀是“Redis 预扣 + RocketMQ 异步落库 + 延迟关单”的组合。

```text
Client
  │ POST /voucher-order/seckill/1
  ▼
VoucherOrderController.seckillVoucher(voucherId)
  │
  ├─ 类级 @SlidingWindowLimit(globalLimit=true)：全局限流
  ├─ 方法级 @SlidingWindowLimit(maxRequests=1, 1min, globalLimit=false)：
  │     单个用户 1 分钟只能抢 1 次
  ├─ RefreshTokenInterceptor：恢复用户
  ├─ LoginInterceptor：必须登录
  ▼
VoucherOrderServiceImpl.seckillVoucher(voucherId)
  │
  ├─ redisIdWorker.nextId("order")：生成订单 ID
  ├─ executeSeckillScript：执行 seckill.lua
  │     Lua 内部：
  │       1) 读 seckill:stock:{voucherId}
  │       2) 库存未初始化 → 返回 3
  │       3) 库存 <= 0 → 返回 1
  │       4) SISMEMBER seckill:order:{voucherId} userId 已存在 → 返回 2
  │       5) INCRBY 库存 -1
  │       6) SADD seckill:order:{voucherId} userId
  │       7) 返回 0
  ├─ 返回码处理：
  │     3 → 尝试按需补热库存，再执行一次
  │     1 → 库存不足
  │     2 → 不能重复下单
  │     0 → 继续
  ├─ markOrderPending(orderId, userId)：Redis 记录 pending，5 分钟
  |  （往redis写入，标记该订单已经提交 MQ，正在等待异步消费创建数据库订单。拦截前端重复点击秒杀，重复请求过来检测 key 存在直接拒绝，避免重复发送 MQ）
  ├─ rocketMQTemplate.syncSend(seckill-order-topic:create, orderJson) 
  |  （普通消息：马上投递，消费者执行真实创建订单、扣库存。）
  ├─ rocketMQTemplate.syncSendDelayTimeMills(order-timeout-topic:close, orderId, 15min) 秒杀订单 15 分钟不支付，自动关闭订单，归还库存
  |  （延迟消息：消息不会立刻被消费，RocketMQ 保存这条消息，15 分钟之后才投递给消费者）
  └─ 立即返回 Result.ok(orderId)
```

异步消费（正常创建订单）：

```text
SeckillVoucherListener.onMessage(message)
  → objectMapper 反序列化为 VoucherOrder
  → voucherOrderService.createVoucherOrder(order)
       ├─ 幂等：若订单已存在，清理 pending 后返回
       ├─ 保存订单
       ├─ MySQL 扣减秒杀库存：stock = stock - 1 AND stock > 0 （乐观锁）
       ├─ 失败则回滚 Redis 库存和一人一单 Set（移除下单集合该用户id）
       └─ 成功清理 pending
```

延迟关单：

```text
15 分钟后 OrderTimeoutListener.onMessage(orderId)
  → SimpleRedisLock(lock:order:timeout:{orderId}) 获取超时关单锁
    （用户在临界时间提交支付，支付线程、超时关单线程同时操作同一个订单，会发生并发冲突）
  → voucherOrderService.closeTimeoutOrder(orderId)
       ├─ 不存在则清理 pending
       ├─ 已支付/已取消则跳过
       ├─ 状态改为 CANCELLED
       ├─ MySQL 库存 +1
       ├─ 回滚 Redis 库存和一人一单 Set
       └─ 清理 pending
```

支付链路与超时关单通过两把不同的 Redis 锁隔离：

- 支付：`lock:order:payment:{orderId}`
- 关单：`lock:order:timeout:{orderId}`

**两把不同名称的锁，使用 SimpleRedisLock（Redis 分布式锁，setnx）互斥保护同一个订单资源**。

面试速记:

> 异步秒杀，请求进来先设置 5min pending 标记防重复，发送普通下单消息，同时发送 15 分钟延迟关单消息。</br>
> MQ 消费者消费下单消息，数据库幂等判断，乐观锁扣库存；成功删除 pending，失败回滚 Redis 库存和一人一单集合。</br>
> 15 分钟延迟消息执行超时关单，使用 timeout 分布式锁；订单未支付就取消订单归还库存；如果已经支付直接跳过。</br>
> 支付流程使用 payment 锁，和关单锁互相隔离，解决支付与超时关单的并发竞争。</br>
> pending 的 5 分钟是 MQ 消费阶段异常兜底，订单创建完成即失效，和 15 分钟支付超时互不干扰。</br>

面试重点：

- Lua 脚本为什么能保证原子性：Redis 单线程执行脚本，库存检查和扣减之间不会插入其他命令。
- 为什么异步：用户无需等待 MySQL 落库，降低 RT。
- 为什么延迟消息：订单超时自动关闭并回滚库存。
- 失败补偿：pending 标记、幂等、Redis 库存/Set 回滚。


## 4. Agent 请求链路

Agent 链路有两种形式：同步接口和 SSE 异步链路。

### 4.1 同步推荐/单店分析

这一类的特点是：HTTP 请求会一直等到 Agent Loop 执行完再返回，中间不推送 SSE，也不落会话消息。它主要用于前端快捷入口：

- 推荐附近美食：`POST /ai/agent/recommend`
- 分析某家店：`GET /ai/agent/analyze/shop/{shopId}`

#### 4.1.1 推荐接口完整链路
整体链路：**HTTP 请求入参 → Controller → Service 组装 Agent 请求 → AgentLoopExecutor 执行 Agent 循环 → LLM 多轮思考 + 工具调用 → 结果回写组装返回给前端**
</br>核心特点：非流式调用，无 SSE 推送，使用空观察者`AgentLoopObserver.noop()`，只收集执行日志，不实时向外输出消息。
```text
POST /ai/agent/recommend
  body: { query, x, y, topK } （x/y：业务上下文坐标参数、topK：返回候选结果数量；）
  │
  ├─ 进入 AiAgentController.recommend(request)
  │     → 只是把 DTO 交给 Service，没有业务判断
  │
  ▼
AiAgentServiceImpl.recommend(request)
  │
  ├─ 构造 AgentLoopRequest:组装agent框架标准入参
  │     prompt = request.query
  │     x      = request.x
  │     y      = request.y
  │     topK   = request.topK
  │     shopId 保持为 null
  │     historyMessages 保持为空，无对话历史
  │
  ├─ 核心：agentLoopExecutor.execute(loopRequest)：执行agent循环
  │     → 这里没有传 StreamingLoopObserver流式观察者
  │     → 因此框架内部降级使用 AgentLoopObserver.noop()，空实现不推送SSE数据流
  │     → 只收集 toolLogs，不推送 SSE，不写工具消息
  │
  ├─ 拿到 AgentLoopResult
  │     ├─ loopResult.agentLoopExecution.status 循环状态：成功/失败/终止
  │     ├─ loopResult.agentLoopExecution.finalAnswer LLM生成的自然语言回答
  │     └─ loopResult.toolLogs 全量工具调用日志，noop观察者收集得来
  │
  └─ 构造 AgentRecommendResponse ：service组装返回对象
        ├─ scene = MULTI_AGENT
        ├─ query = request.query
        ├─ summary = buildAgentLoopReply(execution)
        └─ 如果 x/y 任一为空，设置 missingInfoNotice
```

需要注意：`AgentRecommendResponse.items` 当前没有在 `recommend` 方法中被填充，所以同步推荐主要返回模型生成的 `summary`，不是结构化卡片列表。

#### 4.1.2 单店分析接口完整链路

```text
GET /ai/agent/analyze/shop/{shopId}
  │
  ├─ AiAgentController.analyzeShop(shopId)
  │
  ▼
AiAgentServiceImpl.analyzeShop(shopId)
  │
  ├─ 构造 AgentLoopRequest：后端硬编码拼接
  │     prompt = "请分析店铺ID=" + shopId + " 的真实评价，
  │               重点关注招牌菜、环境和服务"
  │     shopId = shopId
  │     x / y / topK / historyMessages 都为空
  │
  ├─ agentLoopExecutor.execute(loopRequest)
  │     → 同样不接 SSE，只走同步 Agent Loop
  │
  └─ 构造 ShopInsightResponse
        ├─ shopId = shopId
        ├─ summary = buildAgentLoopReply(execution)
        ├─ sampleSize = 0
        └─ sampleSizeNotice 说明当前结果由 ReAct Agent 生成
```

单店分析当前不会固定返回 `positiveTags`、`negativeTags`、`signatureDishes` 等结构化字段，而是由 Agent Loop 决定调用哪些工具，并最终生成自然语言 `summary`。

#### 4.1.3 Agent Loop 内部的真实执行顺序

推荐和分析最后都会进入：

```text
AgentLoopExecutor.execute(request)
  → execute(request, AgentLoopObserver.noop())
  → 创建 AgentLoopResult
  → manualToolAgentLoopExecutor.execute(request, result.toolLogs, observer)
```

`ManualToolAgentLoopExecutor.execute` 内部：
（`internalToolExecutionEnabled = false`：**关闭大模型 SDK 内部自动工具执行**。工具解析、调用、异常处理全部由`ManualToolAgentLoopExecutor`手写代码控制，这也是这个类名字`ManualTool`的来源。）

```text
1. 初始化
   - maxSteps = ai.agent.multi-agent.max-steps，默认 20
   - messages = []
   - messages.add(SystemMessage(systemPrompt()))
   - 如果有历史消息，messages.addAll(historyMessages)
   - messages.add(UserMessage(buildUserPrompt(request)))构造用户侧消息
      /ai/agent/recommend：buildUserPrompt 取request.query用户输入；
      /ai/agent/analyze/shop/{shopId}：buildUserPrompt 取后端硬编码拼接的店铺分析 prompt；
      x/y/shopId 等业务参数部分会在此处做文本注入
   初始化完成后，messages 结构：[System, (历史...), User]，进入循环。
   
2. 记录初始 trace：IDLE ，用于观测链路追踪，配合`AgentLoopObserver`输出生命周期状态

3. 进入 for step = 1..maxSteps
   ├─ 记录 THINKING trace
   ├─ chatModel.call(new Prompt(messages, buildLoopOptions())) 调用LLM
   │     buildLoopOptions：
   │       internalToolExecutionEnabled = false 关闭大模型SDK内部自动工具执行
   │       parallelToolCalls = false 禁止并行工具调用
   │       toolCallbacks = toolRegistry.getToolCallbacks() 传入全部注册工具回调集合，executor根据llm返回的工具名来调用
   │
   ├─ assistantMessage = response.result.output  LLM返回得到assistant角色信息
   ├─ messages.add(assistantMessage) 追加进messages数组
   │
   ├─ 情况 A：没有 toolCalls
   │     ├─ 有文本：FINISHED，finalAnswer = 文本，返回
   │     └─ 没有文本：
   │          blankResponseCount++ 空白回复计数
   │          ├─ 还没到最大步数：追加 blankResponseRetryPrompt，continue
   │          └─ 已到最大步数：ERROR，返回
   │
   ├─ 情况 B：有 toolCalls
   │     ├─ 记录 EXECUTING trace，toolNames 工具名称
   │     ├─ 先尝试 extractTerminateDecision：专门解析是否返回terminate结束工具调用
   │     │     ├─ 只有 terminate，且 answer 非空
   │     │     ├─ FINISHED
   │     │     ├─ terminatedByTool = true,代表 Agent是被terminate工具调用结束，而不是assistant文本结束；
   │     │     └─ 直接返回
   │     │
   │     ├─ 遍历除 terminate 以外的工具
   │     │     ├─ toolRegistry.getToolCallback(name)
   │     │     ├─ 找不到工具：ERROR，返回
   │     │     ├─ toolCallback.call(arguments, ToolContext)
   │     │     ├─ 工具返回结果加入 ToolResponseMessage
   │     │     └─ 写入 toolLogs
   │     │
   │     └─ 如果 toolResponses 非空：
   │            messages.add(new ToolResponseMessage(...)) 写入massages
   │            若是简单推荐场景，追加 simpleRecommendationFinishPrompt
   │
   └─ 进入下一轮 step

4. 循环结束仍未完成
   → ERROR，错误原因 = 超过最大步数
```

#### 4.1.4 同步链路和 4.2 聊天链路的区别

| 对比项 | 4.1 同步推荐/分析 | 4.2 会话聊天 + SSE |
| --- | --- | --- |
| 入口 | `/recommend`、`/analyze/shop/{id}` | `/chat`、`/messages` |
| 是否创建/使用会话 | 不创建会话，不加载历史 | 创建或复用会话 |
| 是否写用户/助手消息 | 不写 | 写 `tb_ai_message` |
| 是否 SSE | 不推 | 推 `status/message/answer_delta/done` 等 |
| 是否异步事件 | 否，直接调用 | 是，事务提交后异步执行 |
| 使用模型 | `ChatModel` 做 Agent Loop | Agent Loop 用 `ChatModel`，最终答案用 `StreamingChatModel` |
| 返回形式 | 直接返回 `summary` | 先返回 messageId，结果通过 SSE 推送 |

对比前面两条同步接口（`recommend` / `analyzeShop`）：

- 同步接口：HTTP 请求同步阻塞，`noop` 观察者，全部执行完一次性 JSON 返回；同步接口是“把用户问题塞进 `AgentLoopRequest`，同步跑完 `ManualToolAgentLoopExecutor`，再把 `finalAnswer` 包装返回”。

- 会话 SSE 链路：**请求‑响应立即返回，Agent 逻辑异步后台跑，通过 SSE 长连接推送中间状态、工具消息、流式答案分片**；具备会话持久化、消息落库、串行会话执行、大模型流式输出

### 4.2 会话聊天 + SSE

整体宏观时序：
1. 前端先建立 SSE 长连接：`GET /ai/agent/conversations/{id}/stream`，会话 ID 绑定连接服务端持有该连接，后续所有事件（status、tool、answer_delta、done）都通过这条通道推送给前端；
2. 前端发 `POST /ai/agent/chat` 提交用户聊天消息；
3. HTTP 接口**立刻返回**会话、消息 ID，不等待 Agent 执行完成；
4. 事务提交后异步监听器触发，后台线程跑 Agent 完整循环；
5. Agent 每一步状态、工具调用、答案分片通过传入的 `streamingObserver` 回调向外 SSE 推送；
6. Agent 循环结束后再流式输出最终答案 chunk，推送完成事件，SSE 通道接收完毕。

```text
前端
  │ 1) GET /ai/agent/conversations/{id}/stream 
  │    前端先建立 SSE，等待服务端推送事件
  │ 2) 前端发 POST /ai/agent/chat
  ▼
AiAgentController.chat
  → AiAgentServiceImpl.createChatMessage
       ├─ getOrCreateConversation 创建/读取会话
       ├─ appendUserMessage 用户消息落库
       └─ publishEvent(ChatMessageCreatedEvent) 发布spring事件
  → 立即返回 { conversationId, chatMessageId }
```
HTTP 到此就响应结束，**不阻塞等待 Agent、不等待 LLM 调用**；Agent 全部逻辑在异步线程后台执行。


事务提交后异步执行：

```text
ChatMessageCreatedEventListener
  @TransactionalEventListener(AFTER_COMMIT)
  @Async("aiAgentTaskExecutor")
  → ConversationExecutionCoordinator.runSerial(conversationId) 会话串行调度器
  → doHandle(event) 真正执行会话agent的逻辑
       ├─ 1.SSE status=queued 推送排队状态
       ├─ 2.loadRecentMessagesBefore(conversationId, chatMessageId, windowSize) 加载会话窗口历史消息
       ├─ 3.agentLoopExecutor.execute(request, streamingObserver) ，组装 AgentLoopRequest，传入流式观察者
       │      ├─ onTrace → SSE status
       │      └─ onToolExecuted → 工具消息落库 + SSE message
       ├─ 4.循环跑完后，流式输出最终回答
       ├─ buildAssistantReply 
       ├─ SSE status=answering
       ├─ streamFinalAnswer：
       │      用 StreamingChatModel 调最终答案整理模型
       │      逐个 chunk 发送 SSE answer_delta
       │      失败则按配置 fallback 分块发送
       ├─ 5.助手消息落库、会话更新
       ├─ appendAssistantMessage
       ├─ updateConversation
       ├─ 6.推送完成事件
       ├─ SSE message(assistant)
       ├─ SSE answer_done
       └─ SSE done
```

- `AFTER_COMMIT`：必须等数据库事务提交完成，用户消息已经落库，才触发；避免读不到刚插入的用户消息；
- `@Async`：切换到 AI 线程池 `aiAgentTaskExecutor`，脱离 HTTP Tomcat 业务线程；
- `runSerial(conversationId)`：**会话串行调度器**，同一个 `conversationId` 同一时刻只会跑一套 Agent 任务；防止同一个会话并发多条消息，messages 错乱、工具并发执行。不同会话之间可以并行。
---------------------------------------------------------

- `SSE status=queued` :推送给前端：任务进入队列，还没开始 Agent 思考；前端可以展示 “排队中” UI。
- `loadRecentMessagesBefore(conversationId, chatMessageId, windowSize)`:从数据库拉取该会话近期历史消息，做窗口截断
- `streamingObserver`：实现两个核心回调，打通 Agent 内部循环 ↔ SSE 推送</br>  `1.onTrace(trace)`：Agent 内部每一步 trace 状态（IDLE / THINKING / EXECUTING / FINISHED / ERROR）转化为 SSE `status`事件推前端； ManualToolAgentLoopExecutor 每一轮循环标记 THINKING、EXECUTING，都会回调 onTrace，前端实时感知 Agent 正在思考 / 正在调用工具。
</br> `2.onToolExecuted(toolLog)`:工具执行完成回调。</br>工具调用记录落库；</br>通过 SSE 推送 tool 类型 message 事件；前端就可以渲染工具卡片（例如 “正在查询店铺评价” 等中间工具过程）。
- **StreamingChatModel做流式输出**:不是前面 ReAct 循环里的 chatModel，是独立流式模型。</br>将 Agent 产出的 finalAnswer 送入整理模型，逐 token 拿到 chunk；</br>每一块通过 SSE `answer_delta`推送到前端，前端做打字机效果；
>架构设计：**ReAct Agent 循环本身是非流式（内部多轮 LLM 是普通 chatModel），Agent 跑完拿到 finalAnswer，再单独过一层 StreamingChatModel 做流式吐出给用户**。
Agent 循环负责思考 + 工具调用；StreamingChatModel 专门负责给用户看的流式打字机输出，两者解耦。

-------
SSE 事件顺序：</br>
`queued` → `thinking` → `executing`（多次，工具调用） → `answering` → `answer_delta*N` → `answer_done` → `done`。



SSE 事件类型：

| event | 含义 |
| --- | --- |
| `connected` | 建立连接 |
| `status` | AgentLoop 各阶段状态 |
| `message` | 工具/助手消息落库后的消息对象 |
| `answer_delta` | 最终回答流式增量 |
| `answer_done` | 最终回答完成 |
| `error` | 处理异常 |
| `done` | 整个请求结束 |

前端读取 SSE：

- `frontend-vue/src/api/modules/ai.js` 中 `streamConversation` 使用 `fetch` + `ReadableStream` 解析 `event:` / `data:`。
- 如果 SSE 失败，前端会降级为轮询 `GET /conversations/{id}/messages`。

### 容易踩坑点

1. SSE 连接晚于 chat 提交：事件发送出去前端没有长连接接收，丢失状态、工具事件；
2. 会话并发：绕过`runSerial`，同一会话多条消息同时跑 Agent，messages 数组错乱，工具乱调用；
3. 窗口 windowSize 设置过小：丢失上下文记忆；过大造成 token 暴涨；
4. 区分两套模型：Agent 循环内部不是流式；流式是 Agent 跑完之后独立做的，不要混淆；
5. 异步线程池耗尽：大量会话同时触发，`aiAgentTaskExecutor`打满，任务全部卡在 queued 状态；
6. 数据库事务：如果事件在事务提交前触发，异步线程查询不到刚插入的 userMessage。
