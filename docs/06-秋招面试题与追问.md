# 秋招面试题与追问

这里的答案要和代码对应，面试时不要背八股，先讲项目事实，再讲你的思考。

## 一、项目整体

### 1. 一句话介绍项目

这是一个“点评 + 秒杀 + 支付 + AI Agent”的本地生活服务项目。传统部分用 Redis 做缓存、布隆过滤器、分布式锁、限流，用 RocketMQ 做秒杀异步下单和延迟关单；AI 部分用 Spring AI + Milvus 实现多轮 Agent、Tool Calling、RAG、会话记忆和 SSE 流式输出。

### 2. 架构为什么这么分

Controller 只负责参数和路由；Service 负责事务与业务编排；Utils 承担通用能力；MQ Listener 和事件监听器处理异步任务。AI 单独放 `com.hmdp.ai`，避免和传统业务耦合，同时 `AgentLoop` 只依赖接口/配置，便于测试和替换。

## 二、缓存相关

### 3. 缓存穿透怎么解决

两层：

1. 布隆过滤器：`ShopServiceImpl.queryById` 先判断 ID 是否可能存在。
2. 空对象：`CacheClient.queryWithPassThrough` 回源后发现不存在，写空字符串，TTL 2 分钟。

布隆过滤器会有误判，所以第二层兜底。

### 4. 布隆过滤器如何初始化和更新

启动时 `BloomFilterInitializer` 删除旧 key，`tryInit` 后分页读 MySQL 主键写入。新增店铺时 `saveShop` 同步 `add(id)`。

追问：

- 如果店铺删除怎么办？当前代码没有删除 bit，因为布隆过滤器不支持精确删除；更严谨方案可以用带删除的 Cuckoo Filter，或定期重建。
- 误判率多少？代码设置 1%，容量店铺 10 万、优惠券 1 万。

### 5. 缓存击穿的互斥锁和逻辑过期有什么区别

- 互斥锁：强一致，但抢不到锁的请求要等待或重试。
- 逻辑过期：高可用，过期后当前请求先返回旧数据，另起线程重建。

项目 `CacheClient` 两种都有实现。店铺详情当前默认 `queryWithPassThrough`，但保留两种击穿方案。

### 6. 为什么店铺详情当前用 passThrough，而不用逻辑过期

这是项目中的一个演进点。README 里说店铺和榜单适合逻辑过期，但 `ShopServiceImpl` 当前实际调用 `queryWithPassThrough`。面试时可以诚实说明：

- 当前生产配置选择了穿透 + 布隆过滤器的组合。
- `queryWithLogicalExpire` 已实现，可切换。

如果面试官追问，可以给出切换逻辑：预热时用 `setWithLogicalExpire`，读时用 `queryWithLogicalExpire`。

### 7. 缓存更新时为什么要先更新数据库再删除缓存

Cache Aside 常用策略。如果先删缓存再更新数据库，可能其他线程把旧数据写回缓存；先更新数据库再删缓存，能减少读到长期脏数据的窗口。仍可能出现极短时间不一致，可通过延迟双删、订阅 binlog、版本号等进一步处理。

## 三、Redis 数据结构

### 8. 附近店铺怎么实现

Redis GEO：

- 按 `typeId` 存 `shop:geo:{typeId}`。
- `GEOSEARCH key BYLONLAT x y BYRADIUS 5000 WITHDISTANCE`。
- 拿到 ID 后回 MySQL 查询，并用 `ORDER BY FIELD` 保持 Redis 排序。

### 9. 关注流怎么实现

发布笔记时，向每个粉丝的 `feed:{userId}` ZSet 推入 `blogId`，score 为时间戳。读关注流时 `ZREVRANGEBYSCORE` 滚动分页。

这是推模式。可以对比拉模式：读时聚合所有关注者，适合粉丝数少的场景。

### 10. 签到怎么用 Bitmap

`SETBIT sign:{userId}:yyyyMM dayOfMonth-1 1`。

统计连续签到：

```text
BITFIELD GET uN 0
然后从低位连续统计 1 的个数
```

## 四、秒杀

### 11. 秒杀完整流程

1. 全局限流 + 用户级限流。
2. `RedisIdWorker` 生成订单 ID。
3. Lua 脚本预扣库存、校验一人一单。
4. Redis pending 标记。
5. 发送 RocketMQ 下单消息和延迟关单消息。
6. 立即返回。
7. 消费者异步落库并扣 MySQL 库存。

### 12. Lua 脚本为什么能防超卖

Redis 执行 Lua 脚本期间，脚本作为一个整体被执行，不会插入其他客户端命令。库存读取、判断、扣减、一人一单检查在同一脚本中完成，因此原子。

### 13. 为什么用消息队列异步落库

- 降低用户等待时间。
- 削峰填谷，保护 MySQL。
- 下单主链路只依赖 Redis，吞吐更高。

代价是最终一致性，需要补偿和幂等。

### 14. 订单超时怎么处理

下单成功后发送 RocketMQ 延迟消息，15 分钟后 `OrderTimeoutListener` 消费，加分布式锁后关闭未支付订单并回滚库存。

### 15. 支付回调和超时关单并发怎么办

支付使用 `lock:order:payment:{orderId}`，关单使用 `lock:order:timeout:{orderId}`。两边操作前都检查订单状态：

- 支付只处理 `UNPAID`。
- 关单只关闭 `UNPAID`。

谁先拿到锁并修改状态，另一方会看到状态已变化并跳过。

### 16. 消息消费失败或重复怎么办

- 落库时先查订单是否已存在，存在则跳过，保证幂等。
- 消费者抛异常让 RocketMQ 重试。
- Redis 预扣失败会回滚库存和一人一单 Set。
- pending 标记用于“订单尚未落库”时的状态查询和失败补偿。

## 五、RocketMQ

### 17. 为什么选 RocketMQ 而不是 Kafka/RabbitMQ

RocketMQ 原生支持延迟消息和事务消息，适合订单超时和削峰；与 Java 生态集成自然。Kafka 吞吐高但延迟消息支持弱；RabbitMQ 延迟消息需要 TTL + 死信队列，复杂度更高。

### 18. 消息模型为什么用 CLUSTERING 和 CONCURRENTLY

- `CLUSTERING`：集群内同一消息只被一个消费者消费，适合订单处理。
- `CONCURRENTLY`：同一消费者组内并发消费，提高吞吐；业务代码内通过幂等和锁保证安全。

## 六、分布式锁

### 19. 手写 Redis 分布式锁如何避免误删

锁 value 使用 `UUID-ThreadId`，释放时执行 Lua：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

判断和删除在一个 Lua 脚本里，保证原子。

追问：

- 锁过期怎么办？本项目业务时间短，设置 leaseTime 5 秒。生产可用 Redisson 看门狗续期。
- 可重入吗？`SimpleRedisLock` 不可重入；Redisson `RLock` 可重入。

## 七、限流

### 20. 滑动窗口和令牌桶对比

滑动窗口统计真实时间窗口，不存在“低峰攒令牌、高峰一起用”的问题，适合秒杀。令牌桶允许突发，但项目场景不希望用户储蓄令牌。

### 21. 限流 key 怎么设计

- 全局限流：`rate_limit:global:{spelKey}:{value}`
- 用户级：`rate_limit:{userId}:{spelKey}:{value}`

秒杀接口做了双层：

- 类级全局：保护系统。
- 方法级用户级：防单人刷接口。

## 八、登录与 ThreadLocal

### 22. 两个拦截器的职责

`RefreshTokenInterceptor` 负责恢复用户并续期，`LoginInterceptor` 负责判断是否需要登录。游客访问公开接口由后者排除，不会因为前者而 401。

### 23. ThreadLocal 为什么最后要 remove

线程池复用线程时，如果不清理，可能把上一个请求的用户信息带到下一个请求，造成越权。`afterCompletion` 统一清理。

## 九、Spring AI

### 24. Spring AI 在项目里做了什么

- `ChatModel`：Agent Loop 思考。
- `StreamingChatModel`：最终答案流式输出。
- `EmbeddingModel`：文档向量化。
- `VectorStore` + Milvus：向量存储和检索。
- `@Tool` / `@ToolParam`：声明工具。
- `ToolCallback`：手动执行工具。

### 25. 内部 tool execution 为什么关闭

关闭 `internalToolExecutionEnabled(false)`，让模型只返回 ToolCall，由自己的 `ManualToolAgentLoopExecutor` 执行。这样：

- 能记录每步状态和工具日志。
- 能控制最大步数、异常、空响应。
- 能处理 `terminate` 这种控制工具。
- 避免框架黑盒自动执行。

## 十、Agent Loop

### 26. Agent Loop 是什么

是代码中的多轮循环：每轮让模型思考，可能输出工具调用；代码执行工具；结果放回上下文；直到模型直接回答或调用 `terminate`。

### 27. 如何避免死循环

- 设置 `maxSteps`。
- 空响应重试提示。
- `terminate` 控制工具。
- 简单推荐场景注入完成提示。
- 未注册工具、工具异常直接终止。
- 每一步记录 trace，便于排查。

### 28. 为什么不用 Spring AI 自动 Agent

项目选择“模型决策 + 代码执行”：

- 可观测性更强。
- 便于限制工具和步数。
- 便于处理业务兜底。
- 适合本地生活场景中相对可控的任务。

## 十一、RAG / Milvus

### 29. RAG 为什么分三个集合

数据类型和用途不同：

- 平台知识库：规则问答，需要关键词 fallback。
- 店铺画像：推荐，需要结构化字段。
- 探店笔记：评论分析，需要标题/店铺名增强。

分开建索引，便于独立重建、过滤和调阈值。

### 30. 知识库为什么加关键词 fallback

纯向量检索对短问题、专业词、高确定性规则可能弱召回。关键词 fallback 直接扫知识文本，保证“库里有 SVIP 规则就能命中”。

### 31. Milvus 和普通数据库的区别

Milvus 存向量并做相似度检索。普通 MySQL 适合精确查询和事务，不适合高维向量近似检索。

## 十二、SSE

### 32. 为什么用 SSE 而不是 WebSocket

当前是服务端单向持续推送，SSE 更轻量。WebSocket 适合双向高频通信。

### 33. SSE 连接怎么隔离

`ChatSseServiceImpl` 用 `StreamKey(userId, conversationId)` 作为 key。每个用户可以有多条 SSE 连接，用 `CopyOnWriteArrayList` 管理。

## 十三、会话记忆

### 34. 上下文窗口怎么控制

每次只加载最近 `windowSize * 2` 条 user/assistant 消息，工具消息不进入模型上下文。降低 token 成本和历史噪音。

### 35. 工具消息为什么要落库但不进上下文

工具日志用于审计、调试、前端展示。如果全部塞进上下文，会快速增长 token；模型需要的是工具调用后的 `ToolResponseMessage`，不是数据库里的 `tool` 展示消息。

## 十四、开放性问题

### 36. 如果流量再大十倍，你会优化哪里

- 秒杀接口继续前置，甚至用独立服务或网关限流。
- Redis 集群/分片，避免单点。
- RocketMQ 多副本、消费组扩容。
- 缓存热点使用本地缓存 + 分布式缓存。
- Agent 使用更细的模型路由、缓存相似问题结果、限制并发。
- 观察慢 SQL、连接池、线程池和 GC。

### 37. 如果面试官让你现场画 Agent 链路

先画四段：

1. Controller 接收请求。
2. 事务提交后发布事件。
3. 监听器异步执行 Agent Loop。
4. Loop 调工具/RAG，结果通过 SSE 推送。

再强调 Loop 内部：Think → 工具调用 → ToolResponse → 下一轮 → terminate/final。

### 38. 项目中你最有把握的亮点是什么

建议选择“手写 Agent Loop + Tool Calling + 三层 RAG + SSE 可观测性”这条线，因为它同时覆盖 AI 和工程能力，也最能体现你读懂了代码。
